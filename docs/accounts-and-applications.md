# Accounts, authenticator codes and private applications

Create an account from the dashboard, choose a lowercase username, and save the server-issued account key before activating it. Existing anonymous cluster ownership and membership keep the same internal principal during this upgrade. Account names are unique and immutable. One account can own applications across multiple clusters, with stable private management URLs such as `/alice/image-worker`.

These URLs are paths on the current Space hostname, not DNS subdomains. A guessed URL does not grant access. Anonymous visitors and other cluster members receive the same not-found/access-denied response for application details. Only explicitly granted accounts can list or inspect private application records. Even the cluster owner needs an application grant to read them. The owner can grant viewer/operator access to registered cluster members, revoke it, or delete the application. Operators can submit/delete application jobs and execute assigned work; viewers can read inputs/results. Only the owner manages grants, application deletion and scoped API keys.

Applications now use the [bounded browser runtime](browser-runtime.md); there is no Dockerfile execution or proxying of always-on websites. Existing CPU/WebGPU demo jobs, nodes and cluster administration remain shared cluster diagnostics and are not associated with private applications. Runtime jobs, logs, environment variables, build inputs and artifacts must use application-scoped authorization when that runtime is added. They must not be routed through the legacy shared demo APIs.

## Keys and sessions

The Rust server obtains 32 random bytes from the operating system CSPRNG for account keys, anonymous bootstrap keys, node connection keys and invite tokens. Account keys are 64 lowercase hex characters (256 random bits). Only SHA-256 digests of high-entropy keys/recovery codes are stored in GitHub snapshots, which are additionally encrypted as a whole with a separate state key. See [database disclosure and migration](database-leak-review.md) for historical-data and rollback limits. Slow password hashing is not substituted for these random credentials; user-chosen passwords are not supported.

Save account keys outside the site, such as in a password manager. The browser keeps only a temporary account session in sessionStorage, not the saved account key. Sessions have a reserved `ms_` prefix, last at most 12 hours, are held in coordinator memory, and expire on coordinator restart. An expired/missing session is rejected with `account_session_required` instead of falling back to an anonymous principal. The UI offers sign-in, keeps remembered node keys and contribution opt-in, and stops further authenticated compute until reauthentication. Reopening/signing in requires the saved key and, when enabled, an authenticator or recovery code. A session is a bearer credential and must also be kept private. Ordinary anonymous identities remain in localStorage for compatibility; new bootstrap identities are generated by the server.

Account creation and rotation have explicit save confirmation. A pending registration can be retried before activation if its key response was lost or the tab was closed before saving. The browser keeps the original anonymous credential until save confirmation, preferring it over a temporary pending account session. After activation, the old anonymous credential is revoked. Rotation first prepares a new key for ten minutes; the old key remains valid until the user confirms the replacement was saved. Confirmation changes the digest and invalidates older sessions. Losing the confirmation response does not lose the already-saved replacement key. Key rotation does not revoke separately issued node credentials: remove a node to revoke its node key.

Explicit sign-out revokes that tab's account session and clears this browser's saved node tokens/settings. Reauthentication to the same account after session expiry can retain remembered node settings; switching accounts clears them. Session revocation applies to subsequent authenticated requests; work already authorized/in flight is not retroactively erased.

New browser node connections send their key as the first WebSocket message over TLS and never put it into the connection URL. The server allows five seconds for authentication and does not register an unauthenticated socket. Old query-token clients remain compatible for migration and should be updated because intermediaries may log URL query strings.

## Authenticator setup

Open **Account security**, enter the saved account key and choose **Set up authenticator**. In an authenticator app choose manual setup, enter the displayed Base32 secret and select time-based codes. Verify a code to enable it. This is standard RFC 6238 TOTP: HMAC-SHA1, six digits, a 30-second interval and one adjacent interval of clock tolerance. HMAC-SHA1 is used for authenticator interoperability; it is not used to hash account keys. Keep device clocks synchronized.

The server generates the authenticator secret and never sends it to a QR/image service. Setup expires after ten minutes. Enabling requires a valid code; each accepted time step is persisted and cannot be reused, including parallel requests. A code used for enabling cannot immediately be reused for sign-in; wait for a new time step or use a recovery code. TOTP is not phishing-resistant.

Eight 128-bit recovery codes are displayed once on enrollment. Save them separately from the authenticator. Each is usable once, together with the account key. Normal sessions require the current account key and a fresh code/recovery code to disable the authenticator or rotate the account key. A session established by consuming a recovery code can reset the authenticator with the saved account key, without spending another recovery code; this lets the last backup code recover an account. This exception applies only to disabling/resetting the authenticator, not key rotation, and ends with the session. Reset immediately after a recovery sign-in, before its 12-hour expiry. Disabling revokes the remaining recovery codes. Reenable to issue a new set. If both the key and all second-factor/recovery material are lost, this anonymous account model has no email recovery or administrator bypass.

Authenticator seeds are encrypted with AES-256-GCM, a fresh random 96-bit nonce and account-bound authenticated data. The encryption key is the 32-byte hex `MESH_AUTH_ENCRYPTION_KEY` Space secret, separate from GitHub snapshots. Deployment creates it with Python's OS-backed `secrets` module only if missing and never prints its value or replaces an existing secret. Preserve it when migrating the Space. Losing it makes existing authenticator seeds unreadable; account-key plus unused recovery-code authentication remains available to disable/re-enroll. For local development supply a private random key; the Playwright configuration uses an explicit test-only key.

Registration is globally rate limited and capped, sessions/pending setups have bounded counts, and second-factor attempts are limited to six per minute per account/purpose. Incorrect root keys are rejected before the per-account TOTP budget so knowing a public username alone cannot exhaust that budget. These are small-deployment controls, not complete denial-of-service protection. Snapshot persistence must succeed before enrollment, recovery-code consumption, credential changes or grants become visible.

## Hosting and decentralized trust

Paths on the same hostname share a browser origin. Arbitrary application JavaScript must not run at the dashboard origin, where it could access browser credentials. These routes serve only the fixed React management interface. Future app websites need isolated origins (for example separate hosts under a domain we control) or a carefully restricted opaque-origin sandbox and scoped messaging. Hugging Face's hostname does not grant us control of wildcard DNS beneath it.

API permissions are not confidentiality from a machine owner executing a workload. An execution node can inspect its assigned plaintext code/data and can fabricate outputs. Future runtime placement must require explicit application trust/worker grants, least-privilege job credentials and a result-verification policy. Hashes and signed custody receipts verify artifact integrity/possession boundaries; they do not prove honest computation. Raw secrets must not be put on arbitrary volunteer workers. Cluster administrators can control pool availability and delete the cluster, which deletes its application records, even without permission to read private records. Removing/leaving cluster membership denies application API access and removes non-owner application grants; owner records remain inaccessible until membership is restored or the cluster is deleted.

Tests cover RFC TOTP vectors, CSPRNG key format/uniqueness, authenticated encryption and tamper/account-binding rejection, replay/recovery rejection, registration/rotation/restart behavior, persistence failure, principal-header spoofing, private metadata grants/revocation and cluster-owner denial. Browser tests cover setup and recovery login, fresh protected application URLs, mobile layout, and first-frame node authentication, alongside the existing recovery suite. This is not a security audit or an implementation of confidential computing.
